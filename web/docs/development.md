# Разработка

## Команди

```bash
cd web
npm install
npm run dev       # dev сървър на http://localhost:5173 (камерата работи на localhost)
npm test          # unit тестове (Vitest)
npm run build     # проверка на типовете + production build в dist/
npm run preview   # сервира dist/ на http://localhost:4173
```

Service worker-ът се регистрира само в production build (`npm run preview` или на сървъра), не в `npm run dev`.

## Тестване на телефон

Камерата изисква HTTPS, а `http://192.168.x.x:5173` не е HTTPS. Има три начина:

1. **Качване на тестов поддомейн с HTTPS.** Най-близо е до реалната употреба.
2. **Тунел:** `npx cloudflared tunnel --url http://localhost:5173` (или ngrok) дава временен `https://` адрес.
3. **Chrome на Android през USB:** `adb reverse tcp:5173 tcp:5173` и после `http://localhost:5173` на телефона. localhost се приема за защитен.

Какво да се сравни с Android приложението, с едни и същи стикери:
- време до резултат и правилни ли са стойностите;
- избледнял печат, малки стикери отблизо, слабо осветление (фенерче);
- Chrome на Android (вграден декодер) срещу `?decoder=zxing` срещу Safari на iPhone.

## Как работи сканирането (накратко)

- `session.ts` праща по **един** кадър наведнъж към worker-а (`createImageBitmap(video)`). Докато той декодира, нови кадри не се взимат, точно като `STRATEGY_KEEP_ONLY_LATEST` в CameraX.
- Worker-ът връща обратно и самия кадър (transferable `ImageBitmap`). `session.ts` пази кадъра с най-много видими баркодове за резултата и затваря (`close()`) останалите, за да не трупа памет.
- Рамките идват в пикселите на кадъра. Overlay-ят ги преобразува с `object-fit: cover`, както `FILL_CENTER` в приложението.
- ZXing връща 1D баркода като тънка линия през чертите, а не като кутия. `boundingBox()` в `decoder.worker.ts` я разширява до поне 15% от ширината, за да работи съпоставянето по IoU/близост в `ConsensusTracker` както с рамките на ML Kit. Ако на реални стикери съседни баркодове се „слепват“ в един трак, тази стойност е първото място за настройка.
- Параметрите на консенсуса (`requiredVotes = 6`, `settleFrames = 20` и т.н.) са същите като в приложението. Уеб декодерът може да е по-бърз или по-бавен на кадър, затова в Авто режим `settleFrames` може да се нуждае от настройка след тестове на телефон.

## Известни ограничения

| | Chrome Android | Safari iOS | Firefox | Chrome desktop |
|---|---|---|---|---|
| Декодер | вграден (ML Kit) | ZXing | ZXing | вграден (macOS) / ZXing |
| Zoom | ✅ | частично (iOS 17+) | ❌ | зависи от камерата |
| Фенерче | ✅ | ❌ | ❌ | ❌ |
| Фокус отблизо | автоматичен | без контрол; не превключва надеждно на макро обектива | | |
| Инсталиране (PWA) | ✅ | „Добави към началния екран“ | ❌ | ✅ |

- Паролата от Wi-Fi код се копира като обикновен текст. Браузърите нямат аналог на „sensitive“ флага в Android 13+.
- На iOS камерата се спира, когато страницата отиде във фонов режим, и се пуска отново при връщане. Същото е направено нарочно за всички браузъри (`visibilitychange` в `main.ts`).

## Следващи стъпки (предложения)

1. Тест на истински телефони (Android + iPhone) със същите стикери като за приложението; настройка на `settleFrames` и на разширяването на 1D рамките, ако е нужно.
2. При слаб фокус на iPhone: подсказка „отдалечете телефона и увеличете с zoom“, когато дълго няма засечени баркодове.
3. По желание споделен код с приложението (Kotlin Multiplatform → JS) вместо ръчния порт. Засега портът е малък (~300 реда), а тестовете пазят съответствието.

## Иконки

`public/icons/*.png` се генерират от векторната икона на Android приложението:

```bash
python3 web/scripts/render-icons.py   # от корена на репото; macOS, нужен е Pillow
```

Скриптът използва `scripts/render-launcher-icons.py` от Android проекта. Ако `web/` се разработва отделно, иконките са вече генерирани и могат да се сменят ръчно (192, 512, maskable 512, apple-touch 180).
